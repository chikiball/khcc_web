01Overview

1.1 Purpose

KHCC Web is a Progressive Web App for KHCC (Knock House Chop Chop), a road-cycling club. It coordinates weekly rides, member profiles, ride leadership, route sharing, and club content — all in one place, on a phone, fast enough to glance at while standing in lycra.

1.2 Scope

This V2.0 document records what is implemented and live at khcc.nandharu.uk, plus what remains in scope for Phase 1 and what is intentionally deferred to Phase 2 or 3. It supersedes the V0.1 draft.

1.3 Out of scope (deliberate)

  • Native iOS/Android apps — PWA only.
  • Payment processing of any kind. The club uses external channels (PayNow, etc.) for membership dues and trip deposits.
  • Strava integration / activity import.
  • Live location / safety tracking (Strava-Beacon-style).
  • Coaching tools, training plans, or AI features.
  • Race calendar, results, season leaderboard.
  • Overseas-trip workflow.
  • Public-facing pages beyond the landing page (everything past sign-in is members-only).

04User Roles & Permissions

Implementation uses a single role column on users with four values, plus a status column for the approval state.

RolePermissionsStatus
MemberRSVP to rides, browse member directory, view own + others' profiles, post photos via gallery (admin only currently). Cannot manage rides.Done
LeaderMember permissions + create / edit / cancel rides, see emergency contacts on rides they're managing.Done
OrganiserSame scope as Leader in current implementation. Reserved for future trip-organiser permissions.Reserved
Admin All accessAll Leader perms + manage members (approve / reject / change role), manage ride types, edit landing-page content, manage gallery.Done

Approval status (users.status)

  • pending — sees /pending screen; cannot use member features.
  • approved — full member access.
  • rejected — sees /pending screen with explanation; auto-flips to pending on next sign-in attempt (re-applying is a one-tap loop, not a permanent ban).

Authorisation is enforced application-side via Server Actions and Server Components calling requireUser() / requireApproved() / requireRideManager() / requireAdmin(). There is no Postgres RLS — the security boundary is the helper layer.

05Functional Requirements

5.1 Phase 1 — MVP Phase 1

FR-1 Authentication & Onboarding Done

  • FR-1.1 — Sign in via Google OAuth or email-credentials (no password, no link). New users land on /pending until admin approval.
  • FR-1.2 — New members must accept the KHCC member agreement (terms / risk waiver) before reaching onboarding.
  • FR-1.3 — Onboarding form: display name, photo, pace group, bike, Strava handle, emergency contact.
  • FR-1.4 — JWT sessions persist across devices. Rejected users auto-flip to pending on re-sign-in.
  • FR-1.5 — Admin invites with pre-assigned role Deferred
Acceptance: A new user goes from landing → signed in → terms accepted → profile completed in under 3 minutes on mobile. ✅

FR-2 Ride Calendar Done

  • FR-2.1 — Scrollable list of upcoming rides (next 14 days), sorted by date.
  • FR-2.2 — Ride card: date/time, title, start point, route preview image (when GPX available), pace badges with per-pace RSVP counts, weather pill (icon + temp + wind chip when ≥ 20 km/h), recurring tag.
  • FR-2.4 — Detail page: description, embedded read-only map with start pin and GPX polyline overlay, route URL, GPX download, full RSVP list per pace, leader credit, full weather block (icon, temp, wind, precip%, sunrise/sunset).
  • FR-2.5 — One-off and recurring rides (weekly / biweekly).
  • FR-2.6 — Statuses: scheduled, weather-watch, cancelled, completed. Per-pace cancellation is also supported.
  • FR-2.3 — UI filters by pace and date range Planned
Acceptance: A member finds and RSVPs to the next matching ride in ≤ 3 taps from /rides. ✅

FR-3 RSVP System Partial

  • FR-3.1 — One-tap RSVP / withdraw. Switching between paces is an atomic upsert (one rider per ride enforced at PK level).
  • FR-3.4 — Per-pace cap visible (e.g. "12/15 spots") on the ride detail page.
  • FR-3.5 — A member sees their own pace highlighted on every ride detail page; RSVPs to past and future rides are queryable per user.
  • FR-3.2 / FR-3.3 — Over-cap waitlist with FIFO promotion Deferred — current behaviour: cap is informational only; admins manually intervene if a pace is full.
  • FR-3.6 — RSVP cutoff time editable by leader Deferred — current behaviour: RSVP open until ride start time.
Acceptance: RSVP state syncs across devices on next page load (no realtime channel; force-dynamic rendering). ✅ for the core path.

FR-4 Member Profiles & Directory Done

  • FR-4.1 — Profile fields: photo, name, pace group, bike, Strava handle, bio, role badge.
  • FR-4.2 — Emergency contact (name + phone) lives in a separate users_private table, only joined in admin / leader paths. Visible to ride leaders & admins on the detail page of rides the member has RSVP'd to. Cross-pace leaders on the same ride can see all riders' contacts (safety).
  • FR-4.3 — Searchable directory at /members with name/bike search and per-pace filter pills. Hidden-from-directory members are excluded from listing but their profile URL still works.
  • FR-4.4 — Privacy toggle: "Hide from directory" on the profile edit form.
  • FR-4.5 — Rider names in any ride's RSVP list are clickable links to /members/[id].
Acceptance: Emergency contact never appears in any non-leader/non-admin code path. Verified by audit of every usage of users_private.

FR-5 Ride Leader Tools Done

  • FR-5.1 — Create / edit ride form: title, datetime, start point with map-tap picker, distance, elevation, route URL, description, multiple pace groups (each with own leader / cap / overrides / notes).
  • FR-5.2 — Cancel ride OR cancel single pace group with mandatory reason. All-pace cancellation auto-cancels the parent ride. Recurring series spawn the next occurrence on cancel so the rides list stays populated.
  • FR-5.3 — RSVP list with emergency contacts visible to managers across all paces of the ride.
  • FR-5.4 — GPX upload at create/edit time. Server parses distance + elevation (Haversine + summed positive deltas with 0.5m noise threshold) and overwrites form values; saves the raw file; generates a static OSM-tile preview image for the rides list.
  • FR-5.5 — Recurring series (weekly / biweekly) created in one form. Lazy materialisation: only one live future occurrence per series exists at any time; the next is spawned by cron / on-cancel.
  • FR-5.6 — Per-ride announcements / pinned notes Planned
Acceptance: A leader creates a recurring Saturday series with three paces in under 2 minutes. ✅

FR-6 Announcements Planned (Phase 1)

  • FR-6.1 — Club-wide pinned announcement banner on /rides.
  • FR-6.2 — Admin / leader posts; members see plain text + optional link.
  • FR-6.3 — Reactions (👍❤️) deferred — keep V1 simple.
Status: The content_blocks CMS already supports admin-edited blocks for the public landing page. An "announcements" block on /rides is a small extension. Not yet built.

FR-7 Notifications Planned (Phase 1)

  • FR-7.1 — Email on member status changes (approved, rejected, access removed) — already wired via SMTP.
  • FR-7.2 — Email reminder 24h before a ride a member has RSVP'd to.
  • FR-7.3 — Email on ride cancellation to all RSVP'd riders.
  • FR-7.4 — Web push (opt-in) — possible but requires VAPID + service-worker plumbing; tradeoff worth discussing before building.
Tradeoff: Web push is high effort for a small club. Email reminders solve 80% of the value at 20% of the work. Recommend ride-cancellation email first, then 24h reminders, then revisit push.

5.2 Implemented features beyond the V0.1 spec

These shipped during Phase 1 and weren't in the original document:

FR-A Multi-pace rides Done

  • A single ride can offer A + B + C (or any subset of ride_types) as separate pace groups. Each has its own leader, cap, distance/elevation overrides, notes, and per-pace status (scheduled / cancelled).
  • One rider per ride enforced at PK level. Switching pace = upsert. Per-pace cancellation supported; if all paces cancel the ride auto-cancels.

FR-B Editable ride types Done

  • Replaces the hardcoded A/B/C enum with an admin-editable ride_types table: code, name, description, color preset, position, active.
  • Admin can add new pace types, rename, change colour, or deactivate at /admin/types. UI tone presets are defined in src/lib/ride-types.ts with literal Tailwind class strings (build-time-discoverable).

FR-C Maps + GPX overlay Done

  • Leaflet + OSM tiles, no third-party API. Touchpad / two-finger zoom enabled. OSM attribution always visible.
  • Admin ride form: tap-to-set start point, fills lat/lng inputs.
  • Ride detail page: read-only map with start pin and dark-blue (#1e40af) GPX polyline overlay when a route file exists. Auto-fits bounds to the polyline.
  • Members can download the GPX file with a slugified filename (e.g. saturday-bunch-east-coast.gpx).

FR-D Static route preview images Done

  • On GPX upload, server stitches OSM tiles using sharp and overlays the route as an SVG polyline, saving a 1024×512 JPEG preview at /uploads/routes/<rideId>-preview.jpg.
  • Used as the cover image on the rides list. Best-effort: failure never blocks the save.

FR-E Weather forecasts Done

  • Open-Meteo (free, no API key, 16-day horizon). Cached via Next.js fetch revalidate: 3600 so 14 list cards don't hammer the API.
  • List cards: WMO emoji + temp + wind chip (when ≥ 20 km/h).
  • Detail page: full forecast block (icon, label, temp, wind coloured red if windy, precip %, sunrise / sunset in location-local time).

FR-F Content + Gallery CMS Done

  • /admin/content — admin edits "About" and "Achievements" blocks shown on the public landing page.
  • /admin/gallery — admin uploads / deletes / edits alt text for landing-page carousel photos. Resized to 1024×1024 JPEG via sharp on upload.

FR-G Member terms acceptance Done

  • A KHCC-specific 13-section member agreement (account responsibilities, data handling, cycling-risk waiver, conduct, content licence, account closure) at /terms.
  • Required checkbox + Continue gate before onboarding. users.accepted_terms_at stamped on submit; existing users prompted on next visit.
  • Re-readable any time via "View member agreement" link in /profile.

06Non-Functional Requirements

6.1 Performance

  • NFR-1 — FCP ≤ 1.5s on 4G, ≤ 3s on 3G. Met (static landing + small RSC payloads).
  • NFR-2 — TTI ≤ 3s on mid-range Android. Met
  • NFR-3 — Server actions p95 ≤ 800ms. Met in normal use; cleanup/migrate operations are slower but rare.

6.2 Accessibility

  • NFR-4 — WCAG 2.1 AA target. Partial — semantic HTML throughout, but no formal audit yet.
  • NFR-5 — Min tap target 44×44pt (gloves!). Met (button { min-height: 44px } in globals).
  • NFR-6 — Pace group never colour-only — always shows the letter inside the hex badge. Met
  • NFR-7 — Respect prefers-reduced-motion. Partial

6.3 Responsive & Device Support

  • NFR-8 — Mobile-first; designs target 375px min width. Met
  • NFR-9 — iOS Safari 16+, Chrome 110+, Firefox 110+, Edge 110+. Met
  • NFR-10 — PWA: installable, offline cache for upcoming rides. Partial — installable + service worker via @ducanh2912/next-pwa; offline cache scope is conservative.

6.4 Security & Privacy

  • NFR-11 — HTTPS / TLS 1.2+ only. Met via Cloudflare Tunnel.
  • NFR-12 — Auth.js JWT sessions; no plaintext passwords (no passwords at all — Google OAuth or email-credential).
  • NFR-13 — No Postgres RLS. Authorisation is application-level via auth helpers. Emergency contact in a separate table that is only joined in admin / leader paths. Rationale: simpler and auditable for a single-app schema.
  • NFR-14 — PDPA-aligned: data export and deletion supported via admin action.
  • NFR-15 — No Strava tokens stored (integration deferred).
  • NFR-16 — Audit columns on rides (cancelled_at / cancelled_by / cancelled_reason) and on member status transitions. Full audit log table not yet built.

6.5 Reliability

  • NFR-17 — Uptime target 99.5% (excl. planned maintenance). Pending live data
  • NFR-18 — Daily DB backups, 30-day retention. Planned — not yet automated; this is the highest-priority operational gap. Current state: docker volume only, single-host risk.
  • NFR-19 — Graceful degradation when Open-Meteo / OSM tiles unavailable. Met — forecast UI hides on null, map shows pin-only without tiles.

6.6 Internationalisation

  • NFR-20 — English at launch. i18n-ready pattern not yet adopted (hardcoded strings).
  • NFR-21 — Dates rendered in browser locale; stored as timestamp with time zone.
  • NFR-22 — Metric units throughout. Imperial toggle deferred to Phase 3.

6.7 Maintainability

  • NFR-23 — TypeScript strict mode. Met
  • NFR-24 — Unit test coverage ≥ 60% on core domain. Not met — no test suite yet. Rely on tsc + lint + manual verification. Next priority alongside backups.
  • NFR-25 — All commits pass npm run lint + npm run typecheck. Met (no CI yet — runs locally before deploy).

10Risks & Mitigations

RiskSeverityMitigation
No automated backups — single-host Postgres volume, no off-box copy. High Build the daily pg_dump + tar uploads/ + rsync-to-off-box cron next.
No test suite — regressions caught by manual click-through. Medium Add Vitest for the small set of pure logic (GPX parse, lazy materialiser, auth helpers). End-to-end can wait.
Single home server — power / network outage takes the site down. Medium Acceptable for a club tool; monitor uptime, document a 30-min cold-restore procedure.
Open-Meteo / OSM dependency — third-party free services could throttle or fold. Low Both are graceful-degraded already (forecast hides, tiles fail loud but page works). Both have alternatives if needed.
Rate-limit self-DoS on admin pages with thousands of rows. Low (mitigated) Hit during the recurring-rides bug; fixed by trimming admin queries to recent + future and disabling RSC prefetch on edit links.
Bus factor of one — single maintainer. Medium Document deployment + restore in CLAUDE.md / runbook. Recruit a second admin.

11Open Questions

  • Should we ship email reminders before push notifications? (Recommendation: yes — covers 80% of value at much lower effort.)
  • Do we need a real audit log table beyond the per-row audit columns we already have? (Recommend: only when admin actions become contentious.)
  • Should the directory be opt-in instead of opt-out? (Currently opt-out via hide_from_directory.)
  • What's the backup destination — another box on the home network, an S3-compatible object store, or rclone-to-cloud?
  • Where do we draw the line on Phase 2 trips? Is the trip-organiser role used at all without that feature, or rename / collapse it into Leader?

12.2 Glossary

  • Pace group — a single tempo / difficulty bucket attached to a ride (e.g. A = fast, B = mid, C = no-drop). Each ride can offer one or more.
  • Series — a recurring ride template (weekly / biweekly). Materialises into actual ride rows lazily — only the next occurrence exists at any time.
  • Materialise — the act of inserting concrete rides rows from a series template.
  • RSVP — a member's commitment to a specific pace on a specific ride. One per (rider, ride).
  • Hide from directory — opt-out of the /members listing. Profile URL still works for anyone who has the link or arrives via an RSVP click.
